# v0.8.1 Bug 清单

v0.8.0 发布后用户反馈「各端 bug 太多」。这份清单记录 v0.8.1 主动排查出的问题：现象、影响、原因、修复、验证方式。
设计层面的问题（层级、动画、透明度、规范对齐）单独记在 [design-audit-v0.8.1.md](design-audit-v0.8.1.md)。

排查方式：Linux 桌面版在 Xvfb 下对本地服务端实跑并逐帧截图；网页版用 Playwright 跑真实端到端；服务端与客户端代码审读；补充单测与集成测试。

## 服务端

### S1 登录没有失败次数限制（可在线暴力猜密码）
- 现象：`/api/login` 可以无限次尝试密码。恢复码接口有限流，登录没有。
- 影响：公网部署时账号密码可被在线枚举。
- 原因：限流器只接在 `/api/recover`、`/api/recovery-code`、`/api/change-password`。
- 修复：新增 `login_limiter`（同一用户名 15 分钟内 10 次、同一 IP 60 次），超出返回 429「密码错误次数过多，请 15 分钟后再试」；登录成功清零该用户计数。
- 验证：`tests/recovery_tests.rs::login_is_rate_limited_per_user`。

### S2 同名并发注册返回 500
- 现象：两个设备同时注册同一个用户名，后到的一个收到「服务器内部错误」。
- 原因：先查后插，插入撞 UNIQUE 约束时被当成内部错误。
- 修复：UNIQUE 冲突映射为 409「用户名已存在」。
- 验证：代码路径审读 + 现有注册测试。

### S3 恢复备份时把所有附件读进内存
- 现象：备份里附件总量接近几个 GB 时，服务器恢复会内存暴涨，小内存 VPS 直接被 OOM 杀掉，账号恢复失败。
- 原因：`open_archive` 把每个附件 `read_to_end` 进 `HashMap<String, Vec<u8>>`，再逐个写盘。
- 修复：解析阶段只记录「附件 id → zip 条目名」，还原时逐条流式解压到暂存目录（256 KB 缓冲），边写边算 SHA-256。
- 验证：`tests/backup_tests.rs` 全部通过；新增 `restore_maps_attachments_with_same_id_prefix`。

### S4 恢复时附件可能对错文件
- 现象：两个附件 id 前 8 位相同（导出文件名就是 `files/{id前8位}-{文件名}`）时，恢复后两个文件块可能指向同一份内容，另一份丢失。
- 原因：用「条目名包含 id 前 8 位」做模糊匹配，取第一个命中。
- 修复：先按导出时的精确文件名匹配，其次 `files/{完整id}`，最后才按前缀。
- 验证：`restore_maps_attachments_with_same_id_prefix`（先写入 b.txt 再写 a.txt，旧逻辑会把 B 的内容给 A）。

### S5 zip 条目声明大小不可信
- 现象：恶意构造的 zip 可以声明很小的 `blocks.json` 大小，实际解压出很大的内容。
- 修复：读取 JSON 条目时按上限 `take(max+1)` 截断并校验实际长度。
- 验证：代码审读；现有路径穿越 / 坏包测试仍通过。
